## 一、需求背景

**目标用户**：员工端＝客户经理（拜访记录提交者本人、需求状态维护者）；团队长端＝团队长（本轮只读，不参与写入）。
**要解决的问题**：两个问题并存。① 拜访记录提交后即固化、无法修改，员工当场填错拜访对象、漏填需求，或事后想补齐信息时无处可改，只能作废重填或放任记录失真。② 需求跟进（Demand）与拜访记录各存一份「需求状态」，两条写入路径互不相通——需求详情改为「已满足」后拜访记录仍显示「未满足」，反之亦然，团队长看到的上下文不可信。解决后：员工可在**拜访详情页进入编辑态修正／补齐原记录字段（任意「拜访」记录均可修改，2026-11-10 修订取消原限制）**；需求状态在两端共享同一份值，任一端修改即时反映到另一端的所有展示位。
**竞品差异 / 品类惯例**：本次未做外部调研（既有功能域的局部改造），不适用。
**AI 能力边界**：不适用。

## 二、逻辑补齐摘要

### 2.1 主成功路径

- **路径 A（拜访记录补充与修正）**：员工在「历史拜访记录」点开**任意一条「拜访」记录** → 拜访详情页 → 点导航栏右上「修改」→ 进入编辑态表单（原记录字段全部预填）→ 修改／补齐字段 → 点「保存修改」→ 校验通过后覆盖原记录 → 返回详情页展示更新后内容，历史列表该行同步刷新。
- **路径 B（需求状态同步）**：员工在「需求跟进」列表打开一条需求详情 → 修改「需求状态」→ 保存更新（**停留当前详情页**并 Toast「需求状态已更新」，不返回列表）→ 详情页「当前状态」标签与需求跟进表对应行状态标签、计数即时刷新；该状态同时同步到对应拜访记录的详情页、历史列表行与首页时间轴（反向亦然：拜访编辑表单改状态即覆盖需求侧）。保存后停留口径以《2026-11-03-需求跟进连续阅读-spec.md》2.2 分支 6 为准。

### 2.2 关键分支

- **分支 1 · 可修改判定（2026-11-10 修订）**：**所有「拜访」记录一律可修改**——详情页导航栏右上恒展示「修改」入口，可修改性**不再**依据关联需求状态判定（进入详情页不再读取关联需求状态）；原「关联需求已全部满足 → 不可修改 / 展示不可修改说明条」分支及其只读态已取消。**「活动」记录仍不提供「修改」入口。**
- **分支 2 · 可改字段**：编辑态开放全部表单字段（拜访对象、银行需求挖掘、达成合作内容、需求是否满足、需求是否紧急及解决方案、其他拜访信息）；**打卡凭证（打卡网点／地点、打卡时间）为只读凭证，不可改**。
- **分支 3 · 需求状态双向共享（后写覆盖）**：
  - **状态枚举统一**：需求状态统一为 `已满足 / 未满足 / 无法满足` 三态；需求详情现有的「无法解决」更名为「无法满足」，与拜访表单一致。
  - **需求侧 → 拜访侧**：需求详情保存状态 → 以 recordId 关联的拜访记录的需求状态同步为该值（**仅限已关联记录**）；拜访详情页标签、历史列表行、首页「渠道拜访」时间轴、团队长端只读展示全部随之刷新。
  - **拜访侧 → 需求侧**：拜访记录修改表单改「需求是否满足」→ 覆盖对应需求的状态。**取消既有「仅在需求仍为未满足时才跟随、终态不覆盖」的限制**，任何状态下都跟随变更。
  - **后写覆盖**：两端都可写入，以最后一次保存为准直接覆盖，不做终态保护、不做冲突提示（二次确认仅沿用需求详情既有「未保存改动拦截」规范）。
  - **关联与粒度（可选关联，非一一对应）**：拜访记录与需求跟进**不强制一一对应**。按 PRD §5.4：满足条件的「**未满足**」需求提交后生成 Demand 记录并进入需求跟进；需求跟进**不一定**来自拜访记录（后续支持在需求跟进表独立新增，原型尚未实现，本轮不涉及）。当需求跟进与拜访记录**存在关联**时，以 recordId 绑定，两者的需求状态与内容共享同一份值、双向同步、后写覆盖；**未关联的需求跟进不参与同步**。
  - **内容类联动（沿用）**：改「需求挖掘」内容／紧急程度／解决方案 → 同步更新该记录已生成的对应需求内容。
  - **条目增删（沿用）**：新增需求项与新建口径一致——满足条件的「未满足」需求提交后生成 Demand 记录并进入需求跟进；移除需求项时其对应需求若仍为「未满足」则同步失效，已是终态（已满足／已关闭／已失效）的不受影响。
- **分支 4 · 记录类型**：本次仅覆盖**拜访记录**；历史列表中的**活动记录**详情页不提供「修改」入口。
- **分支 5 · 未触发同步**：未进入编辑、未点击保存时不产生任何写入，各展示位读同一份状态即天然一致。

### 2.3 状态与异常

- **状态**：
  - 可编辑态：**所有「拜访」记录**，详情页导航栏右上展示「修改」入口，内容只读（2026-11-10 修订：取消原「关联需求未全部满足」前置条件，不再有「只读态 / 不可修改说明条」）。
  - 编辑态：表单已预填原记录字段、字段均可改；打卡凭证区只读展示。
  - 活动详情：不展示「修改」入口与说明条（不适用）。
  - 需求状态：已满足 / 未满足 / 无法满足三态，两端共用同一份值。
- **异常**：
  - 校验失败：可见必填模块未完成 → 阻止保存，模块标红「必填未完成」并 Toast「请完善相关信息」（沿用新建口径）。
  - 保存失败：Toast「保存失败，请稍后重试」，停留编辑态，已填内容不丢失；需求状态保存失败时保留当前页面与已选状态并提示失败。
  - 连续多次保存：以最后一次为准。
  - 「其他」备注：Q1／Q2／Q3 选择「其他」时对应备注必填（沿用新建口径）；隐藏字段不参与校验。
- **回退**：编辑态点「取消」→ 丢弃本次修改、返回详情页（详情页保持原内容，不落库）；系统返回／左滑等同「取消」。需求详情的「存在未保存改动」拦截沿用既有规范，本次不变。

### 2.4 跨页影响

- **入口页**：员工端「历史拜访记录」列表（整行点击进详情，入口不变）；首页「渠道拜访」时间轴／日历当日记录卡；员工端「需求跟进」列表与需求详情。**列表行不新增直接修改入口**。
- **结果页**：拜访详情页（保存后原地展示更新后内容、需求状态标签刷新）；需求详情（保存后停留当前页并刷新，不返回列表）。
- **被动影响页**：
  - 历史拜访记录列表：保存后该行摘要按更新后内容刷新（拜访对象摘要、需求状态标签）；需求状态标签读取共享状态值。
  - 首页渠道拜访时间轴／日历：只读更新后记录，需求状态标签读取共享状态值。
  - 需求跟进（Demand）：**已关联拜访记录**的需求跟进，内容联动更新；状态与拜访记录双向共享、后写覆盖；未关联的需求跟进不参与同步。
  - 团队长端（团队总览／拜访记录／员工详情·拜访只读详情／员工详情·需求跟进／需求管理 Tab／上报需求列表与详情中的「员工侧当前需求状态」）：只读读取共享状态值，**不开放任何写入口**。
- **不涉及**：活动记录详情页、待补充记录队列、打卡凭证生成逻辑、拜访次数统计与日历打点、团队长端处理动作（标记跟进／归档）。

### 2.5 仍未决项

无阻塞项。以下两项登记为后续范围，不影响本次执行：
1. 需求跟进表「新增需求」入口（PRD §5.8「支持新增（首版占位）」）：原型尚未实现，不在本轮范围。
2. 团队长端「归档」与需求状态的锁定 / 联动关系（本轮明确排除）。

## 五、验收标准

1. **主路径可完成（拜访编辑）**：**任意一条「拜访」记录**，详情页右上点「修改」→ 编辑态（字段预填）→ 改字段 →「保存修改」→ 覆盖原记录 → 详情页展示更新后内容、列表该行同步刷新。
2. **可修改判定正确**：**所有「拜访」记录**（含关联需求已全部「已满足」的记录）展示「修改」入口，详情页顶部不出现「关联需求已全部满足，不可修改」说明条；**「活动」记录详情不展示「修改」入口**。
3. **可改字段正确**：6 模块字段均可改；打卡网点／地点、打卡时间为只读凭证不可改。
4. **校验一致**：编辑态可见必填模块未完成时阻止保存，标注「必填未完成」+ Toast「请完善相关信息」；「其他」备注必填沿用。
5. **需求状态同步成立（需求 → 拜访）**：员工端需求详情把状态由「未满足」改为「已满足」并保存 → 需求列表该条为「已满足」；打开其已关联的拜访记录详情，需求状态标签为「已满足」；历史列表行与首页时间轴一致。
6. **反向与后写覆盖成立（拜访 → 需求）**：**任意「拜访」记录（含关联需求已全部「已满足」的记录）** 在修改表单把「需求是否满足」改为「无法满足」并保存 → 需求详情与需求列表展示「无法满足」（同一枚举）；两端先后修改同一状态时最后一次保存的值生效。
7. **保存后不回退为只读**：保存后返回详情页仍展示「修改」入口，不因关联需求状态变为不可修改、不出现说明条。
8. **团队长端一致**：团队长端拜访只读详情与需求跟进展示的状态，与员工侧最新状态一致。
9. **回退正确**：编辑态「取消」丢弃修改、返回详情页（原内容不变、不落库）。
10. **范围守界**：第四节列出的项均未变化（活动记录详情、待补充队列、打卡凭证属性、团队长端读写边界、统计口径、归档动作）。

## 六、风险与依赖（可选）

- **依赖**：需按 recordId 读取原记录全字段回填编辑态，并提供原记录更新保存接口（服务端）；保存需幂等，避免重复提交。
- **依赖（2026-11-10 修订）**：可修改性判定**不再**依赖「按 recordId 读取关联需求状态」，也不再要求原型演示态保留「可编辑／不可修改」两种样本——所有拜访记录均可修改。
- **依赖**：已关联的需求跟进与拜访记录的需求状态需按 recordId 共享一份值，两端写入同一份数据，否则做不到「任一端修改即时同步」。
- **风险**：本 Spec 已取消既有「不覆盖已处理状态」口径（原《2026-11-03-拜访记录补充与修正-spec.md》§2.2 分支 3 与 §2.4），两份原件已合并为本文件；如有其它文档引用旧口径需一并更新。
- **风险**：需求「条目新增／移除」仍保留「已终态需求不受影响」的例外（见 2.2 分支 3），与「状态后写覆盖」并存于同一字段族；若产品要求口径完全一致，需再确认。
- **风险**：编辑态与新建态共用表单，需确认「手动地点（无打卡网点）」记录进入编辑态时打卡凭证区的只读表现。
- **风险**：`§5.6` 原明文定义为「只读」，本次已修订该定位，并已同步更新两份 PRD 的页面定位描述与验收口径。
- **风险**：原型中「需求跟进列表」与「拜访记录」的需求描述文案目前互不一致，需先对齐为同一需求内容，关联映射才能演示；该对齐属本 Spec 3.2 点名范围。
